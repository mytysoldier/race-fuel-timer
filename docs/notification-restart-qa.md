# 再起動後の予約通知残留・修正とQA（#83）

## 原因と修正

予約IDと操作IDはメモリ内だけにあり、プロセスを作り直すと前プロセスの未配信予約を取り消せなかった。修正前のテストでは、同じ通知センターを保持したままschedulerを再生成し、ランAの3件とランBの3件が計6件残ることを再現した（期待3件に対して失敗）。

- 起動時と `beginNotificationOperation()` で、OSの未配信予約を取得して以前の補給通知を整理する。
- 補給通知用の `reminder-` 接頭辞に限定し、照会完了時点の有効な操作UUIDを持つIDは残す。照会中に新しいランが始まっても、その予約を削除しない。
- 新しい予約追加は整理タスクを待ち、有効な操作IDを再確認してから行う。待つのは照会と取消要求の送信までで、OS内部の取消完了を同期的に保証するものではない。旧IDだけを指定するため、その後の新IDへの追加を一括取消で消すことはない。
- 通知なしで開始するときも予約操作を開始し、古い予約を整理する。セッション・記録の保存形式、通知間隔・終了予定・本文、Live Activityの仕様は変更しない。

対象は未配信の予約。配信済み通知の履歴は削除しない。[Appleの取消API](https://developer.apple.com/documentation/usernotifications/unusernotificationcenter/removependingnotificationrequests%28withidentifiers%3A%29)は非同期で未配信の指定IDを取り消す。[予約取得API](https://developer.apple.com/documentation/usernotifications/unusernotificationcenter/getpendingnotificationrequests%28completionhandler%3A%29)で取得するのも未配信予約であり、通知センターに見える配信済み履歴とは分けて確認する。

## 自動検証

Xcode 26.2、専用iPhone 17 / iOS 26.2 Simulator（`159D6FCC-F4BD-48FA-A3A9-B6B2C7BFCF55`）。`xcodebuild test -parallel-testing-enabled NO` で既存36件＋Swift Testing追加5件、計41件成功。

1. scheduler再生成・新ラン開始後に旧ランの予約が残らない。
2. 起動だけで古い補給予約を消し、別用途のIDは保持する。通知許可を要求しない。
3. 通知なしの新操作でも古い補給予約を消す。
4. 起動時の照会が新ランの予約追加後に返っても新ランを消さない。
5. 整理待ち中に操作IDが変わると旧操作は追加を再開しない。

既存の記録中の取消、通知許可待ちの操作変更、追加中の終了、停止／再開のテストも成功。`make lint` / `make typecheck` / `make build` 成功。

## SimulatorでのOS予約ID確認

2026-10-26 JST、10分間隔・4時間（24件）の本番ターゲット。OSの未配信予約IDと追加予定秒数だけを出力する**一時的な診断ビルド**を使用した。診断ログは最終ソースから除去し、最終ビルドもログなしへ戻した。ログは `docs/.local/issue-83/` に保持し、コミットしない。

| 操作 | OS APIで確認した結果 |

| 対象アプリだけを `simctl terminate` でプロセス終了 | セッション非永続のまま再起動する条件を作成 |
