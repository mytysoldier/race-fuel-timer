### 実ルートの実機検証手順案

実行条件: 本人が検証に同意したiPhoneで、ヘルスケアに経路付きのランがあり、試作が読み取れること。現在の試作は最新30件のみ検索し、表示するランを選ぶ機能はない。経路のないGarminのランだけではこの検証を完了できない。別の人に依頼する場合も本人の同意を得て、その人の端末で操作してもらう。募集や連絡はこの手順の対象外。

1. 端末・OS・試作ビルドを記録し、本人がデータの有無と、ワークアウト・経路の読み取り許可を確認する。実際の座標やルート画像を記録・送信しない。
2. 試作で「HealthKitのランを読み込む」を選び、結果を成功／見つからない／エラーとして記録する。見つからない場合は権限拒否と断定せず、アクセス設定、経路付きランの有無と検索対象を確認する。
3. 表示された場合、本人が元の記録と見比べて、全体の形・分断・欠損・日付や取得できた数値が妥当かを確認する。各区間の先頭・末尾が実際の開始・終了とは限らないため、保護を有効にしても位置特定を防ぐ保証はしない。試作の各区間端方式はSimulator専用で、実機では未検証。
4. 本人が保存を希望する場合に限り、位置特定のリスクを確認して写真へ保存し、背景・線・記録がプレビューと一致するか確認する。共有は送信先と内容を本人が選ぶ場合だけ試し、キャンセルと完了を区別する。不要な実ルート画像や共有先のコピーは本人が管理する。
5. 結果は操作・成否・不具合・未確認事項を記録し、日時、距離、地名、正確な経路、画像や健康情報を公開Issue・ログに載せない。元記録と一致したかの判断は本人の確認として記載する。失敗や空結果も成功扱いせず、他のラン・分断・遅延追加などはそれぞれ別に確認する。

## HealthKit

- 読み取り対象はランの `HKWorkout` と `HKWorkoutRoute`。HealthKit capability と読み取り目的の説明が必要。書き込みは要求しない。
- 読み取り許可の拒否とデータが存在しない状態は確実に区別できない。空状態では「ルート付きのランが見つかりません。ヘルスケアのアクセス設定や記録を確認してください」と案内し、拒否と断定しない。期間限定の読み取りにも対応する。
- ワークアウトの保存後にルートが追加・更新され得る。対象ワークアウトのルートは anchored query で追加・削除を追跡し、各ルートの位置情報は route query の複数バッチを完了まで受け取る。最新のランにルートがなければ古いランも探し、更新時には再検索できるようにする。検索件数や負荷の上限は実測して決める。
- データベースがロック中に利用できない場合、取得失敗として再試行を案内する。位置をログに出力しない。

根拠: [ルートの読み取り](https://developer.apple.com/documentation/healthkit/reading-route-data)、[アクセス許可](https://developer.apple.com/documentation/healthkit/authorizing-access-to-health-data)、[HealthKitの設定](https://developer.apple.com/documentation/xcode/configuring-healthkit-access)。

## 保存と権限変更時の設計案（2026-11-01）

以下は #105 の設計であり、本番実装はまだない。2026-11-01、ユーザーは保存後のアプリ内での見返しは完成画像でよいことと、iPhoneのバックアップに作品を含めることに合意した。その他の詳細は引き続き検討する。

| 方式 | 見返し・編集 | 保持と注意点 |
| --- | --- | --- |
| HealthKitから毎回再生成 | 読み取り可能な間は見返せる。背景・色などの再現には別途設定の保存が必要 | 元のランや読み取り権限がなくなると再生成できない。作品の見返しを保証できない |
| 完成画像を端末内に保存（採用方針） | 保存時の作品を権限変更後も見返せる。線色や背景の再編集には元データからの再作成が必要 | 生の座標を長期保存しないが、画像の軌跡・日時等から場所が推測され得る。画像は端末のバックアップに含める |
| 座標と編集設定を端末内に保存 | 権限変更後も再編集できる | 座標そのものを長期保持するため、削除・バックアップ・漏えい時の影響が大きい |

採用方針に沿った具体案:

- 作品作成中の座標・ラン情報は処理に必要な間だけメモリで扱い、ログや分析、独自サーバーに送らない。画面を離れる時や再取得前に作業中データを破棄し、古い非同期処理の結果が新しい画面に戻らないようにする。OSや他アプリの挙動まで含めた完全消去は保証しない。
- ユーザーがアプリ内に保存した完成画像は、既存の履歴ファイルとは別の `Application Support` 配下に保存する案。保存するのは画像と、一覧や削除に必要な最小限の管理情報とし、元の緯度経度やHealthKitオブジェクトは保存しない。画像にはルートの形など機微な情報が残る。保存失敗・破損・空き容量不足では成功と表示せず、一覧で破損項目に安全に対応する。
- 写真への保存や共有は別の明示操作とし、アプリ内保存しただけで写真への追加や共有はしない。アプリ内で作品を削除しても写真・共有先・バックアップに存在するコピーは別管理であり、削除前に分かるよう案内する。写真・共有先からの削除をアプリが保証しない。
- 保存作品はユーザーが削除するまで保持する候補。HealthKit権限の取消や元ランの削除に連動して勝手に削除しない。ユーザーの合意により作品を端末のバックアップに含める方針。`Application Support` は通常バックアップされるが、設定や復元条件によって異なるため、実装後に確認し、機種変更時の復元を保証したことにしない。写真ライブラリや共有先の同期・バックアップも別の設定に従う。端末内処理だけでもバックアップやユーザーによる共有を無視して「端末外に出ない」と断定しない。
- 読み取り開始時は取得中、取得結果なしは権限拒否と断定せずアクセス設定・記録を確認する案内、エラーは再試行を示す。既存作品の閲覧は読み取り失敗に依存させない。新たなルートの取得が必要な画面は前景復帰時に表示中の取得結果をいったん隠して再取得し、失敗や結果なしの場合に古いルートを新しい取得結果として残さない案。画面切替中や一時的なエラーでもプレビューが消えるため、操作の負担は検証する。HealthKitは読み取り拒否をアプリに直接通知しないため、取消だけを確実に検出する方式にはしない。
- 写真アプリに保存した画像の削除、アプリ削除時や機種変更時の挙動、バックアップからの復元、画像への位置情報メタデータ、権限取消後の保存作品閲覧を実装時にそれぞれ確認する。既存の `savedReminderPlan` と `session-history.json` は移行・削除しない。ユーザー自身の写真を背景に使うか、その権限・元画像の保持・位置情報は別途未決定。

保存後の再編集は不要で、端末バックアップに含めることにユーザーが合意した。保存数の上限、画像形式と容量、ファイル保護、権限取消時の前景復帰UXは実測・検証して決める。これらが決まるまで実装Issueの確定条件にしない。

根拠: [HealthKitの読み取り権限](https://developer.apple.com/documentation/healthkit/authorizing-access-to-health-data)、[ファイル保存場所とバックアップ](https://developer.apple.com/documentation/foundation/using-the-file-system-effectively)。既存の設定・履歴は `ReminderPlanStore.swift` でそれぞれ `UserDefaults` と `Application Support/session-history.json` に保存している。
